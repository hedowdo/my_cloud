# Architecture and integrity contracts

Status: local foundation and Stage 3 identity; Stage 4 durable file backend is implemented; Stage 5 file UI/previews/icons have passed local acceptance; spatial features remain Stage 6. Owner authorized Stage 2 on 2026-10-20. See `plan.md` for stage dependencies and the accepted conditional development recommendation. Cloud eligibility and recovery release gates remain open.

## Boundaries

`frontend/src` contains React components and a separate fetch client. Vite development proxy and Compose Caddy proxy keep API requests same-origin. No credentials, private storage keys or domain rules in components. `backend/app` owns configuration, health and DB connection lifecycle; later API routers call authorization and domain services, which coordinate repositories/storage. No file/account routes are stubbed as successful operations.

PostgreSQL stores metadata only. Actual files/icons belong to the dedicated file volume, outside the static document root. `database_data` and `file_data` named volumes survive container recreation. PostgreSQL role `postgres` is bootstrap-only; `cloud_migrator` owns application schema, while `cloud_app` gets DML/usage rights without superuser or schema-creation privileges. Compose does not pass bootstrap/migration credentials to the runtime API. For production, refine table-specific permissions and audit immutability before release.

The local API explicitly refuses non-development environments. Stage 2 offers only health and development OpenAPI. It must not be publicly hosted without authentication, secure cookies, authorization and deployment hardening from later stages. No production-ready claims are made from local health checks.

## Initial schema: `0001_foundation`

UUIDs are generated by application code; all timestamps are PostgreSQL `timestamptz` in UTC; sizes are signed 64-bit byte counts. Tokens store hash bytes, never plaintext. String enums use database CHECK constraints so they are explicit and straightforward to migrate.

| Table | Fields and invariants |
| --- | --- |
| users | Unique normalized `email_key`, original email, password hash, admin/member role, active flag, light/dark preference, creation timestamp. Registration cap and account lifecycle are transactional Stage 3 services, not seeded users. |
| sessions | User FK, unique token hash, CSRF hash, created/last-seen/idle/absolute expiry and revocation timestamps. Lifecycle/expiry enforcement is Stage 3. |
| invitations | Creator FK, unique token hash, expiry after creation, redemption/revocation, redeemed-user FK. Default 24-hour lifetime and single-use transaction are Stage 3. |
| blobs | Unique generated 64-hex storage key, SHA-256 digest, size 0–500,000,000, bounded media type (safe octet-stream default), staging/durable/deleting lifecycle. MIME/name never determine on-disk path or alone authorize preview; validated classification is Stage 5. Icons use separate blob references with stricter validation. |
| items | Self-referencing parent, file/folder kind, name/normalized key, uploader, blob/icon FK, positive revision, created/updated/trash actor/time, replacement-of reference. Folder has no content blob; file requires blob. Only seeded root may lack parent; direct self-parent forbidden. |
| positions | One shared coordinate pair per item, finite bounded coordinates and positive revision, updater and time. Placement belongs to the item's current folder; moves handle coordinates transactionally. |
| activity | Actor FK, explicit action allowlist, target UUID/name snapshot, UTC time/request UUID and bounded-by-service JSON object. Target has no item FK so deletion doesn't erase historical identity. No automatic audit purge. |
| upload_reservations | Actor/parent/blob references, reserved/received bytes, lifecycle and expiry. Received may never exceed reserved/file limit. |
| namespace_lock | Singleton row used with `SELECT ... FOR UPDATE` by later identity/storage mutation services to serialize registration/quota/tree critical sections for this small user count. |

The only seed is root folder UUID `00000000-0000-0000-0000-000000000001`. No default passwords, admin, invitation or user data. Do not rename/move/trash/delete the root: service-level guards are required before file routes exist. Live siblings have a partial unique `(parent_id, name_key)` index excluding directly trashed items. Descendants of a trashed folder retain their own metadata/keys and are filtered by ancestor traversal. Ancestor cycles, parent-kind validity, blob durability, five-user limit and subtree operations require locked service transactions; a FK alone does not enforce them.

## Chosen implementation defaults

Session proposal: 24-hour idle and seven-day absolute expiration; revoke on logout/deactivation. Invitation: 24 hours, unique single-use revocable token. Names: normalize Unicode NFC and casefold for collision key; preserve display name, reject separators/control characters/dot names and overlong names. Keep Both allocates unique normalized keys under the namespace lock. Exact Unicode key rules must be shared across all name mutation routes and tested.

File maximum: decimal 500 MB, 500,000,000 bytes, enforced while streaming including missing/misleading Content-Length. Upload proposal: four simultaneous globally, two per user, with disk/workspace reservation checks. Revision mismatch returns 409; coordinates use the same conflict policy. Replacement keeps stable item identity and retains old content as a trash recovery item; no silent overwrite or auto-purge. These defaults are now documented for the approved Stage 2 contract; feature implementation still requires the corresponding stage approval.

## Storage transaction protocol

1. Authenticate/authorize; lock namespace row, validate live destination/tree, revision/collision decision, pool/concurrency and physical-disk headroom; create reservation and staging blob record. Commit reservation before accepting bytes.
2. Stream outside a DB transaction into a generated-key staging path on the same persistent filesystem, count received bytes, hash and abort at reserved limits. No whole-file buffering. Clean up interrupted requests through durable lifecycle/reconciliation, never by guessing references.
3. Flush/fsync file, atomic same-filesystem rename to final private key, fsync directory where supported; mark durable and publish metadata/audit/reservation completion atomically after revalidation under lock. PostgreSQL cannot atomically commit filesystem writes, so crash reconciliation is mandatory.
4. Replacement never releases old bytes from quota while retained. Deletion marks persistent jobs/state before bytes are unlinked; final metadata and audit survive partial filesystem failures. Never delete a blob still referenced by live/trash/recovery/backup-consistency state.

Global mutation locking is deliberately simple for at most five users, but streaming never holds it. Stage 4 implements and tests this lifecycle; Stage 5 adds the full file-management interface.

## Migrations and recovery

Alembic files contain immutable, explicit DDL; later changes add revisions, never change an applied revision. Only the separate migration service runs `upgrade head`; readiness checks exact schema revision and file-volume write access. API startup never creates/drops tables. Runtime readiness failure returns 503 without DSNs/SQL/filesystem details.

Test empty upgrade, repeat upgrade, disposable downgrade/base, re-upgrade and actual pg_dump/pg_restore, then process restart and persistence. Production migrations require verified backup and a release-specific rollback plan; downgrade is not automatically safe. Windows native PostgreSQL tests do not substitute for Linux/ARM64 Compose tests. No automatic production updates/merges.

## Stage 3 identity boundaries

`identity_security.py` owns strict inputs, token digests and bounded Argon2id work. `identity_service.py` owns PostgreSQL transactions, sessions, invitations, rate buckets and active/role policy. `identity_routes.py` owns HTTP inputs, response models, exact Origin checks and cookies. `metadata_boundary.py` limits actual bytes before parsing. `bootstrap.py` is the interactive first-admin-only CLI. React has a separate identity client, login/redemption screen and minimal administrator controls; hiding controls never grants or denies API access.

Additive revision `0002_identity` creates bounded HMAC-keyed rate counters and expands security audit actions. Readiness requires this exact revision. Existing Stage 2 roles/metadata/file volumes are preserved. No accounts are seeded by migrations. The downgrade refuses populated new security history; rollback must use an approved verified backup rather than erase audit records. Disposable tests clear only their guarded, harness-created identity fixtures before downgrade rehearsal.

## Stage 4 file boundaries and persisted jobs

`file_models.py` defines strict inputs/public output allowlists and the normalized name/byte contracts. `file_store.py` owns generated-key .staging/.objects paths, restrictive creation, symlink refusal, fsync/rename and file-descriptor reads. `file_upload.py` drives incremental python-multipart callbacks, actual byte/disk checks, checksum and transfer leases. `file_service.py` owns locked namespace/quota/publication/recovery/audit policies. `file_routes.py` owns protected JSON/streaming HTTP boundaries and download completion semantics; `reconcile.py` is a local maintenance CLI.

Revision 0003_files adds persisted JSON upload intents, deletion_jobs and item-to-job links. Revision 0004_transfer_parents makes the destination FK nullable with ON DELETE SET NULL, preserving active transfer reservations after parent deletion until cleanup; deleting a referenced blob clears the reservation reference; a removed replacement target clears its recovery relationship without destroying the retained recovery bytes. Downgrade refuses nonempty lifecycle intents/jobs. Production rollback remains an approved backup operation.

Every mutation verifies active session, CSRF and administrator role where needed inside the shared namespace transaction. Streams do not hold that namespace lock. PostgreSQL advisory transfer leases prevent a reconciler from cleaning an active writer; disk-check/write advisory transactions serialize actual disk consumption across processes. The existing five-connection pool supports four leased uploads plus a metadata/write transaction. Finalization rechecks the current destination/target revision and session before publishing metadata; failures preserve prior visible content.

An upload starts with a committed blob/reservation row before any byte file exists. Body chunks are bounded at 64 KiB; file bytes are fsynced and renamed before the metadata/audit transaction commits. After an uncertain commit, cleanup obtains a fresh locked DB read and refuses to unlink any referenced bytes. Abandoned registered staging records older than two hours are reclaimed only with a nonblocking advisory lease; no unknown file is guessed to be disposable. Reconciliation also resumes previously confirmed deletion jobs, never ordinary trash.

Permanent deletion records a job and marks a selected trashed subtree unavailable, retaining charged bytes until unlink completes. Unlinks only target blobs with no outside references. Partial failure leaves a pending job with a non-sensitive error code; retries handle already-missing files and finish metadata/audit only after all target unlinks succeed. An open download owns a file descriptor, so Unix unlink does not corrupt its reader; Windows defers failed unlinks until a later retry after the handle closes.

Local capacity defaults are deliberately 1 GB counted shared pool plus a 2 GB filesystem emergency reserve; no 100 GB cloud capacity is claimed. Trash, recovery copies, deleting bytes and in-flight reservations count. Admission checks both quota and actual filesystem free space; chunk writes recheck physical reserve. Desktop Docker's virtual filesystem is not proof of host backing-disk headroom; keep the local test pool bounded and monitor the host separately. Verified OCI capacity/disk ledger remains Stage 8.

Limits: 64 nesting levels, 10,000 items per subtree mutation, 100 items per list response, offset at most 100,000. Stage 5 may add richer search/filter/sort/cursor UX. Downloads are safe attachments, with a stable opened descriptor and checksum metadata. Audit reports server stream completion/interruption; it never asserts the client saved the file. Same-size silent disk corruption is not recomputed on every download; checksum verification/recovery remains part of backup acceptance.

## Stage 6 spatial boundaries

file_positions.py extends the existing authenticated router with folder-scoped placement reads, idempotent missing-placement initialization and position updates. Existing namespace locking serializes initialization and concurrent first/subsequent writes. Parent plus item revision prevents a stale drag from restoring an old coordinate after a move away/back; position revision prevents one user silently overwriting another. No applied migrations change.

SpatialCanvas owns local viewport, pointer capture, logical coordinate conversion, five-second placement refresh and explicit conflict retry. Position refresh is ignored during an active drag/save; file-list refresh is explicit. The SVG connector layer batches faint connections into one path with a separate highlighted path; only the first 40 orbs animate, and folders above 100 shown nodes disable orb animation/shadows and the decorative core pulse. Reduced motion stops orb/core animation. api/spatial.ts contains pure fit/zoom/delta geometry. Saved coordinates are independent of viewport and decorative transforms. Keyboard focus reveals offscreen nodes at a usable scale without moving the node during pointer selection. A stable desktop details column prevents the first click moving a node before a double click; tablet details use the existing stacked layout.

Missing positions initialize in 250-ID requests below the 16 KiB JSON cap. Canvas metadata is capped at 500 matching children (five bounded browse pages); a visible limit notice and paginated list/grid preserve discovery. Cross-folder searches and viewports narrower than 768px use list/grid. Saved-position reads cap at 10,000 per folder, matching the existing subtree-operation bound; exceptionally large folders should use list view. Pan, zoom and coordinate writes are bounded. The spatial experience adds no network service, asset host, runtime dependency or cloud cost.
