# Stage 3 implementation scope — 2026-10-21

Owner explicitly authorized "ok stage 3 now" after Stage 2 acceptance. Work remains local on `stage-3-identity`. Stage 4+, cloud writes, deployment and main merge are not authorized.

Implement backend identity modules (validation/Argon2id, PostgreSQL repository/service, session authorization and routes), an additive migration for durable rate-limit buckets, interactive first-admin bootstrap, React login/invitation/account and minimal administrator invitation/user controls, configuration/locks and meaningful security/integration/browser tests. Preserve existing volumes; execute tests against newly generated disposable databases/projects. No default owner password or public bootstrap endpoint.

Chosen defaults: 24-hour idle/seven-day absolute sessions; 24-hour single-use/revocable invitations; five registered users including inactive accounts; Argon2id 64 MiB/three passes/one lane with two concurrent hash operations; passwords 12–128 characters without trimming; validated normalized email. Tokens are 256-bit random values, with only SHA-256 digests stored in PostgreSQL. Each login/registration rotates the session and CSRF token; password/invite/session tokens never appear in logs, URLs sent to the server or list APIs. Invitation links carry the token in a fragment, removed from the browser address after reading.

Secure/HttpOnly/SameSite=Strict host-only session cookies are the default. A separate readable, equally scoped CSRF cookie supplies the header whose digest must match the session. Every mutation checks exact allowed Origin; authenticated mutations additionally check CSRF. Login/redemption accept only bounded JSON bodies and trusted origins. Local HTTP uses an explicit development-only loopback exception, with separate cookie names; production HTTPS/Secure-cookie acceptance remains mandatory before deployment. No wildcard CORS or forwarded-IP trust. Rate limits use the actual socket peer (proxy-shared budgets are conservative locally; production trusted proxy configuration is a release gate).

Rate limits persist in PostgreSQL, keyed with a dedicated HMAC secret, bounded bucket retention/count and atomic updates. Registration/invite redemption/admin mutations share the namespace lock; final authorization and active-account checks occur inside the same locked transaction. First-admin creation is allowed only with an empty user table. Prevent self-deactivation and loss of the last active administrator. Deactivation revokes existing sessions. UI role visibility supplements server-side authorization.

Test gate: bootstrap/no-default-admin; signup/login/logout; generic login failure and Argon2id storage; cookie flags; session rotation/expiry/revocation; CSRF/origin/oversize/extra-field rejection; inactive/non-admin/unauthenticated direct access; expired/revoked/reused/concurrently redeemed invites; concurrent registrations for the last slot; rate limiting and spoofed-forwarded-IP resistance; private logs; migrations/restart/persistence; desktop/mobile/keyboard/browser workflows. Do not check off unexecuted checks.

Security references: [Argon2 API](https://argon2-cffi.readthedocs.io/en/stable/api.html), [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [OWASP sessions](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). These inform implementation; passing local tests does not imply public deployment readiness.
