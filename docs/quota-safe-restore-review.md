# Prelaunch native restore review

Prepared 2026-10-23 after the first native backup became AVAILABLE. Proposal only; no disk has been detached, deleted, restored, copied or replaced. The current source is the 150 GB hedowdo-data volume in hedowdo-backups, attached to hedowdo-hub. The application/database have not been started, and there are no real-user production uploads on this volume. Its prepared release and configuration are still important and must be preserved.

The 50 GB boot plus 150 GB data disk fully uses the 200 GB free live-volume allowance. A parallel 150 GB restored volume would total 350 GB and is not permitted under the strict $0 plan. A full-size restore can instead release the prelaunch source disk before creating its replacement, but this is destructive and requires specific owner approval. Resource availability is not guaranteed: failure to recreate the volume could delay launch. The source disk's deletion cannot simply be undone; recovery depends on the retained backup or verified safety copy. No instruction in this proposal authorizes deleting the backup or boot disk.

Exact proposed sequence; destructive source-storage and cloud-resource changes require specific approval. A private, reversible boot-disk safety copy can be prepared first without changing the source:

1. Re-inventory source/boot volumes, backup slots and free-tier/home-region evidence. Re-fetch the exact baseline backup and require AVAILABLE, correct source identity, FULL and size 150 GB. Record the immutable backup identity from private capture evidence. Refuse any concurrent application/container or resource changes.
2. Preserve a private root-only safety copy of the unused mounted data filesystem on the existing boot disk, with adequate measured free space and a hash/ownership/mode manifest. Do not print production configuration or copy it into Git/chat. Verify every file and required metadata before source removal; refuse incomplete or changed data. Retain the native backup separately. This safety copy does not replace native recovery evidence or create extra cloud capacity.
3. Stop Docker on this otherwise unused host, sync and unmount the exact data filesystem. Detach only the identified data-volume attachment through the owner console, confirm the detached volume's full identity and then delete only that original 150 GB volume. Never format or delete the boot disk. These destructive steps require a specific owner confirmation of the named source and recovery procedure.
4. Wait until the source has been released and fresh inventory shows only the 50 GB boot allocation. Inspect the restore form for exactly one 150 GB Balanced/10 VPU replacement in the same home region/AD, compartment hedowdo-backups, Oracle-managed encryption, auto-tune/replication off. Do not submit a parallel disk, a larger size, paid fallback, different region or changed performance tier. Confirm the exact restore form before submission.
5. Restore only the retained verified baseline to that replacement volume, wait AVAILABLE and attach paravirtualized read/write to the existing VM with in-transit encryption. Check the new provider identity/device and exact restored filesystem UUID before mounting. Never run mkfs: a restored disk already contains the filesystem.
6. Verify the original file hashes, owners, modes, source manifests, environment file permissions and host preflight against the restored filesystem; verify no boot-disk fallback. Update the approved source-volume identity for future backups and the attachment inventory. Keep Docker stopped until the recovered mount/preflight passes. This drill covers provider full-size volume recovery of the prelaunch material; production DB/application consistency, daily coordination and restore acceptance still need their separate tests.

No original backup or safety copy is removed in this proposal. Do not activate backup deletion, scheduling or notifications as a side effect. Do not call the restore tested until the actual replacement and verification complete. Native restore orchestration is not granted to the VM's limited backup dynamic group; destructive resource actions require the owner's console access rather than widening the VM's IAM permissions.

Cost expectation: live disk capacity falls from 200 GB to 50 GB then returns to 200 GB; retained baseline continues using one of five backup slots. Expected $0 only within the verified eligibility/configuration. Existing prepared release and DB-free state make this a prelaunch opportunity; it is not approval to repeat destructive recovery against real-user storage later.

Relevant repository boundaries: AGENTS.md requires explicit approval for destructive operations and review of cloud changes. The native restore gate in recovery-runbook.md is not waived by this proposal. [Oracle allowance](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm).
